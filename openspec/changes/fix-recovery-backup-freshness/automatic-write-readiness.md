# Automatic Assisted Backup writes: implementation gates

R4 requirements reconciled 13 October 2026 from audit starting app head `b160656218dc6065ad12af9db220c974255bfc23`. The original plan reviewed Keeper `0550ac9ffa938a079816ae4ed58bc970324c3e08` and Relay PR #4 `82ee3b10708a56d220170505d1bb7e3bc8429e77`; those are historical inputs, not the final proof source.

The owner requires the automatic-backup fix and disposable proof in R4. Critical native IOS/ANDROID backup checks also precede release; explicitly physical-only follow-up may be recorded separately. The implemented committed-payload/session proof has observed host Realm/transactional HTTP evidence in [automatic-write-validation.md](automatic-write-validation.md) and [October evidence](evidence/automatic-backup-source-proof-2026-10-13.md). `AUTOMATIC_BACKUP_SOURCE_READY=true` permits only development loopback testing while `AUTOMATIC_BACKUP_RELAY_ROLLOUT_READY=false` keeps hosted writes fenced. This record authorizes no production enablement, merge or Relay deployment.

## Why the audit-baseline intent cannot authorize a write

At the audit starting source, `BackupWriteIntent` recorded the selected account session and a previously verified Relay revision. It did not identify the local recovery state represented by an encrypted payload or deletion. `backupPost` therefore rejected all seven operations before network. That was required at the baseline: some producers encrypted action data before Realm persistence, Realm could change while an action waited, and one action could emit several Relay writes with the same captured base revision. A valid server compare-and-swap protects against another server writer; it does not prove that the client is sending its present local recovery data. These historical observations are superseded for the final implementation by the source/proof result matrix.

The baseline central Realm observer invalidates backup verification **before** each relevant write. It has no post-commit token and can fire for several field writes in one logical action. The baseline transport's `queuedMutationRevisions` is never populated, so it cannot provide a queue completion proof. A pre-send comparison of a prepared ciphertext against the current Realm image is necessary but still insufficient for operations deliberately sent before local persistence.

## Implemented transaction model

1. Give each logical local recovery operation an account-scoped operation ID and a commit result. A successful commit captures a monotonic recovery generation after all related Realm writes; failed or partial writes stay pending and never authorize upload. For pre-persistence producers, stage data locally and queue the cloud mutation only after this commit. Do not make server success a prerequisite for saving a new wallet, signer, vault or deletion.
2. Capture the originating `appId`, account session, verified base revision/epoch and operation ID before async work. Never substitute a newly verified base for an older action. On A→B→A, reject old queued work even if A is selected again. An already sent request has an uncertain outcome and requires readback.
3. At the head of the per-account queue, re-read the fresh local recovery image and prove the proposed operation's decrypted payload or deletion target against that image and its committed generation. Verify the selected account, backup consent, encryption key ownership, and the originally captured session immediately before sending. An operation-specific failed proof ends in pending/unverified without network.
4. Read or retain a validated protected-v3 namespace snapshot, complete raw projection checksum and original revision/generation/authEpoch tuple. The original Keeper App/provider identity remains separate. No legacy endpoint fallback. Apply each proposed operation to the remote snapshot in memory and reject an effect that removes remote-only recovery records or changes key identity without an explicit user decision. The Relay must atomically enforce original `expectedRevision`, `expectedGeneration` and `authEpoch`, returning a positive acknowledgement with its own advancing `newRevision`, `newGeneration` and correct `authEpoch`.
5. A multi-record logical operation should use one Relay transaction carrying all its effects. When protected mutations are sequential, each step must validate its own current local proof and use the preceding acknowledgement’s complete revision/generation/epoch tuple. Partial success remains pending. Never call the whole backup verified on an intermediate response.
6. After the last acknowledged write, read back and decrypt the complete Relay image. Only a match with a newly captured local image at the same committed generation may set verified. A local write during comparison invalidates the claim. The existing atomic Redux verification commit remains the final UI gate.
7. On 409, old Relay/404, malformed acknowledgement, timeout, lost response, network error, failed local commit, changed session or changed local generation, stop the chain. Do not retry prepared ciphertext or send later fanout members. Keep pending and run a read-only check. A lost response may have committed on the server; its result must be learned from readback before any fresh write.

## Operation-specific proof at the queue head

| Relay operation | Local proof before send | Historical audit-baseline producer complication |
| --- | --- | --- |
| `updateAppImage` | Decrypt each wallet/USDT/signer ciphertext with the active account seed; map IDs, sanitized signer records and recoverable fields must equal the committed Realm records. `replaceNodes` requires the exact current normalized node set; app metadata must come from the current KeeperApp. | New wallet and signer creation call backup before Realm insertion. Node and version paths use different timing. Action payloads may be stale. |
| `migrateXfps` | Old exact KeyUID must be absent in committed Realm; new exact KeyUID and decrypted sanitized signer must match Realm. Verify all affected vault signer references, and prove the old map entry exists in the validated Relay snapshot. | The baseline worker updated a live signer before building the request. It previously sent bare fingerprints while Relay maps use KeyUIDs; the baseline narrow fix still left automatic transport disabled. |
| `deleteAppImageEntity` | Every wallet/USDT/signer ID must be absent after a successful local commit and present in the expected Relay snapshot. Deleting a signer must not make a retained vault unrecoverable. | Baseline BTC wallet and signer deletion called Relay before Realm deletion; USDT deletion did so directly. Reordering required durable pending state and truthful result/UI handling. |
| `deleteVaults` | Each ID must be absent after local commit; other participant/shared-vault references must remain owned and recoverable. | Vault deletion also calls Relay before local deletion. A remote success followed by local failure can leave a mismatched backup. |
| `updateVaultImage` | Decrypt the vault; its ID, sanitized signers, policy, archive state and `signersData` must match the committed Realm Vault plus persisted VaultSigner registrations. | Creation and metadata edit can call Relay before persistence. Registration changes can fan out to several vault writes; migration creates and archives two vaults. |
| `modifyLabels` | Decrypt each added label and verify the account-derived hashed ID and current Realm tag. Every deleted hashed ID must map to a tag absent after local commit. Reconcile add/delete overlap and account ownership. | Imports, upgrades and transaction-label workers can emit multi-label fanouts; a delayed file callback carries older intent. |
| `deleteBackup` | Require explicit Delete protected backup for the same selected account/session and original protected namespace/revision/generation/epoch. Preserve local records and consent until positive scoped acknowledgement plus complete tombstone readback. Older encrypted copies remain read-only; an uncertain reply never means Delete succeeded. | This is a destructive exception to the local-image comparison: the user intentionally removes the remote copy while keeping Realm. It needs its own opt-out state and separate tests. |

## Test matrix and remaining enablement gates

Run each of the seven operations against disposable Realm and transactional Relay fixtures, with real encryption/decryption and the production saga/transport entry points. For each operation, verify: matching committed payload/target reaches the protected mutation route once; stale payload after a local mutation sends nothing; A→B→A sends nothing; a server 409/old route 404/malformed response leaves pending and does not fall back; timeout or lost acknowledgement sends no next item and readback cannot create false verified. Exercise both matching and remote-only/conflicting snapshots.

Add focused multi-write fixtures for (a) creating and archiving a vault, (b) one VaultSigner registration affecting several vaults, and (c) label import plus deletion. Make the first Relay write succeed and the next fail; assert local data survives, the remaining prepared writes do not run, and neither a saga nor Redux reports verified. Assert a local mutation injected just before the final verification commit leaves the backup pending. Pair these tests with native iOS/Android create, edit, delete, relaunch and clean Recovery Key restore on the exact app SHA, plus exact protected-protocol HTTP tests against a disposable replica set.

The host source matrix now supports development loopback testing. Preserve the hosted rollout fence until transaction topology, compatible running Relay artifacts and protection from old/legacy writers are reviewed under separately authorized rollout. A source pass is not deployment evidence. A future source change must never turn an endpoint name or revision string alone into a freshness proof. The current result matrix identifies which source/fixture cases actually ran and keeps native app relaunch, critical IOS/ANDROID and release checks open independently of host results.
