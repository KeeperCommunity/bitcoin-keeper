# Installed parent admission: source preparation A

This source package prepares the authority boundary for the five remaining
canonical software parents. It installs no profile, pin, credential or private
caller. The committed `INSTALLED_PROFILES` in `installed_parent_window.cjs` is
empty. All actual requests block before any public/private API access.
Canonical `collect` continues to write only BLOCKED readiness, with five
`NOT IMPLEMENTED` parent cases and no positive attestation.

## Existing installed public origin

`canonical_native.collectInstalledPublicEvidence` freshly verifies the existing
protected current `sprint` source S, installed workflow S, official Actions app,
latest exact run/attempt, required successful platform jobs, bounded original
ZIP bytes and complete public raw metadata. The dedicated Variables reader
must freshly read `KEEPER_CANONICAL_NATIVE_DRIVER_SHA`. Only complete raw checks
mint an immutable WeakSet public proof. A serialized/copy object cannot mint it.
The proof includes independently fetched worker-source hashes; those are not
projected into the old canonical attestation schema. Public facts alone never
supply private parent credit.

Before issuing that proof, the collector rechecks both selected artifact API
identities after all platform downloads and the commit-tree read. It then runs
the live protected-source/workflow/run/attempt/pin fence as its final API phase.
An earlier platform artifact expiring or changing during the later read, or a
pin/source/run revocation during the tree read, must reject the whole collection.
Nine host race controls reproduced proof issuance on the original source and
reject it after this correction. This is a bounded repeated read, not an atomic
GitHub snapshot or live installed/native verification.

## Additional atomic reviewed window

`authenticateInstalledParentWindow(github, context, request, {pinReader})`
requires a committed finite installed profile, then reuses existing canonical
origin/live-pin checks. It strictly parses the original UTF-8 value of
`KEEPER_CANONICAL_PRIVATE_WINDOW_JSON` (maximum16KiB) using the same dedicated
read-only Variables client. Unknown fields, duplicate decoded keys, missing
identities and mismatched source trees/runs fail closed. Origin/live pin is
checked again before capability issuance. No ordinary Actions-token fallback
is allowed.

Every SHA/hex identity must be a literal string before its regex is evaluated.
Parsed JSON arrays and coercible objects cannot stand in for window IDs or
controller trees. The original c030 checkpoint's latent type-coercion acceptance
is preserved; the descendant rejects it under the synthetic installed-profile
controls. Actual installed policy remains empty throughout.

Exact top-level keys are `schema:1`, `profile`, `window_id` (64 lowercase hex),
`app`, `backend`, `public` and `private`:

- `app`: `{repository,sha,tree}` for `KeeperCommunity/bitcoin-keeper`, app S.
- `backend`: `{repository,sha}` for Relay baseline `29597b27...`.
- `public`: `{workflowPath,workflowSha,ref,runId,runAttempt}` for the installed
  canonical workflow/S/protected `refs/heads/sprint` and actual numeric IDs.
- `private`: exact `IOS` and `ANDROID` descriptors, each
  `{platform,app,control,backend,execution}`. `control` is
  `{repository,sha,tree}`. `execution` is
  `{repository,workflowPath,workflowSha,ref,runId,runAttempt}`. The workflow SHA
  equals that platform's actual controller SHA. Controllers and run IDs differ.

A future reviewed profile must fix private repository ID496119449, finite
integration workflow/ref, D448 reviewed driver baseline, backend295 and
`D448_RAW13`. Live variable data cannot populate the empty committed policy.
There is no source/controller self-hash cycle: a future exact live window is
selected after app/controller commits and actual runs exist. Independent public
and private windows prove their own built/installed bytes from the same app
S/tree; no cross-window binary hash equality is assumed. A non-app reader's
reviewed source SHA is independent from app S.

`revalidateInstalledParentWindow` requires the issued WeakSet capability, freshly
rereads origin/live pins and rejects any changed original manifest bytes.
Capabilities contain no credentials and always retain release/readiness/
authorization/execution flags false. They authorize only subsequent read-only
evidence collection, not a native run or account operation. The separate stacked
consumer package must collect original D13 proofs freshly; it cannot cast a
previous diagnostic record or use this capability as a software pass.

## Local source before imports

All three existing canonical provenance/worker/collector scripts bootstrap the
approved raw guard #7125/22ae, Git blob
`2c36d299851261d68965d37dbda024b950d46d8d`, before importing repository code.
They require literal regular guard paths, owner0100 consistent with its regular
Git file, a single link and the exact captured bytes. They compile the captured
approved bytes and call `verifyRawCheckout(root,context.sha)`, which checks all
tracked raw Git blobs, literal file identities and owner0100. This does not
widen the event wrapper's manual routes or replace canonical origin/live pins.
The read credential is removed from `process.env` before Git/Python subprocesses.

Host controls use real disposable Git repositories for hidden index-flag edits,
different same-tree commits, byte changes, symlinks, hardlinks and executable
modes. Installed-profile controls evaluate a synthetic source copy with a test
profile; production exposes no policy override. These are host software checks,
not native/installed/physical results.

Remaining one-time inputs require explicit approval to install reviewed source
and caller, a finite installed profile, an exact atomic window variable and
appropriate dedicated read identities. No pin write, credential provisioning,
merge/protected promotion, native scheduling, signing, upload or release action
is performed here. Security findings, excluded storage redesign, physical and
biometric checks remain separate and unwaived.
