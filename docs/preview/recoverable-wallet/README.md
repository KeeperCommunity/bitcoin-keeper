## Second client checkpoint in this branch

- The separate preview app starts with **no wallet** and the three choices directly on Wallets: **Single-Key Wallet** (phone or signing device next), prominent **Seedless Wallet**, and **Custom Wallet**; Import Wallet remains visible. The same chooser is retained for Add Wallet. The labels describe setup paths, without a “Featured” badge or a blanket seed-word promise on the card. Single-Key, Custom, and Import explain their preview limits. A guarded normal-app entry and no-default-hot-wallet setup path are also coded, but their gate requires the exact testnet preview identity; that identity currently launches the isolated shell. They are deliberately dormant until an integrated preview runtime can be reviewed. With the gate off, normal Keeper retains its existing wallet creation behavior.
- Selecting Seedless immediately starts a compact, simulated progress screen rather than a mandatory introduction: Mobile Key then Server Key status labels advance in order, Hardware Key waits for the user, and **Choose Hardware** enables only after both demo steps. “How it works” is optional in-flow detail; the complete policy remains a required review before any real wallet could be created. The timer changes labels only: it creates no key, backup, server registration, or wallet. A future real “Added” status must wait for verified secure Mobile Key persistence or Server Key registration, respectively; elapsed time cannot establish readiness.
- The default Seedless design calls for an independently generated Mobile Key and no new seed words for the user to record. Derivation from Keeper's existing 12-word Recovery Key remains an **optional creation path**, not a setup prerequisite or chooser message. The isolated BIP85 helper reserves a versioned child range starting at index 1,000,000; Keeper already reserves 0–99 for default hot wallets and 100–199 for USDT, so the first or tenth child must not be shared with Seedless. Its pure allocator refuses to reuse an ordinal, including after deletion, but it is **not connected to wallet creation**: Realm lacks the durable reservation ledger, tombstones, and atomic backup mapping it requires. A Recovery Key cannot recreate a separately generated Mobile Key by derivation alone; that would require a reviewed encrypted backup or wrapping design.
- A public-only testnet policy builder validates distinct Mobile/Hardware/Server keys, BIP48 account tpub shape, supported import transports, and an optional absolute Inheritance Key locktime before the final review. A separate pure importer accepts public Coldcard/Jade BIP48 testnet exports and marks both the device and policy **not verified**; it does not open a device or connect to the UI. The 2-of-3 and delayed 2-of-4 policy results remain explicitly **unfundable**. The inheritance Miniscript is a review candidate, not a verified descriptor or hardware registration. See [policy-draft.md](policy-draft.md).
- A client-only Recovery Contact state model covers encrypted-cloud readback receipts, offline retry, invitation/request expiry, approval/decline, and optional recovery-code gating. It stops before cryptographic enrollment or restoration. No contact key, encrypted backup, native cloud container, or independent exchange channel exists yet. See [recovery-contact.md](recovery-contact.md).
- The isolated preview now lets the owner explore Recovery Options after the Seedless walkthrough: separate Cloud Backup and Recovery Contact screens show unverified readback, simulated offline/retry, sample invitation and lost-phone decisions, decline, and expiry. Every screen states that no key, encrypted blob, contact credential, approval response, or restored Mobile Key exists. These are decision samples, not an operational recovery path.
- Proposed inheritance behavior is a fixed on-chain unlock date selected before wallet creation, with no reset on app open; changing it later requires a new wallet and on-chain transfer. The heir needs the Inheritance Key **and** an accessible original signer independent of the Server Key. The preview labels this proposal as unconfigured. Product decisions about fixed versus renewed timing, an extra contact recovery code, and the heir's second signer are pending owner answers.

## Non-negotiable product model

- One Wallet within Keeper; not a replacement for whole-app recovery with the twelve-word **Recovery Key**.
- Standard base **2-of-3 Mobile Key + user-selected Hardware Key + Server Key**. Mobile/Server status is presented automatically; no manual quorum builder.
- Hardware added last among the base keys, using appropriate physical connection, QR or NFC flow.
- Optional Inheritance Key is chosen before final wallet-policy approval. The *final complete* policy is confirmed once; don't fund/register an intermediate wallet.
- Plain base 2-of-3 is not Bitme's timelocked Miniscript descriptor. When inheritance is added, use Keeper's Miniscript policy with compatibility testing for **all** signers. Signing-only hardware (TAPSIGNER/Satochip) is distinct from policy-verifying hardware.
- After inheritance eligibility, independent heir's Inheritance Key + any eligible original signer can form the required 2-of-4 quorum; Keeper server cannot become mandatory for the heir's exit path.
- Cloud encrypted Mobile Key backup in user's iCloud / Google Drive is separate from existing Personal Cloud Backup. Its "healthy" status must be based on cryptographic read-back, not request success.
- Hardware-authorised unlocking via server-held recovery material is an accepted trade-off; design, isolation, replay protection and threat model require independent security review before real funds.
- Contact-based recovery must ultimately be **independent of Keeper's server** if an enrolled contact + accessible encrypted cloud backup are available.
- Hardware + Server supports delayed replacement of missing Mobile Key when cloud backup is missing, once server implementation is allowed.
- Mobile + Hardware and descriptor support server-independent spending/exit. Test actual external-wallet compatibility; public descriptors do not contain private keys.
- Key changes mean new wallet policy and on-chain transfer with fee and original-wallet authorization. Archive the complete predecessor and monitor retained archived addresses indefinitely, including zero-balance wallets. Do not archive merely because the same Mobile Key was restored.
- Keep Recovery Contact distinct from signing keys and Inheritance Key. The existing 12-word Recovery Key is an **additional option**, not a mandatory prerequisite or a message on the Seedless choice. Do not imply it can reproduce an independently generated Mobile Key without an encrypted copy or other reviewed recovery mechanism.

## How the owner will test it

Deliver a **separate-installation iOS and Android Keeper Preview** (different app identity and storage namespace from production Keeper), testnet-only and isolated from real iCloud/Google Drive backups. Verify the necessary app IDs, native entitlements, cloud containers and distribution access before promising TestFlight or Android APK builds. Keep normal Keeper installed and unaffected. Preview actions may initially be mocked: they must be unmistakably identified as simulated; no fake success, funding or cryptographic-security claims.

A new preview checkpoint is complete **only after an installable build and a short device-specific owner test checklist are available**, and after actual tests are recorded:

1. **Prototype/UI**: start on empty Wallets or use Add Wallet, choose Seedless Wallet, then review hardware picker/connection, automatic Mobile/Server status, optional inheritance, and one final policy; include errors/cancel/resume.
2. **Disposable real wallet**: create fixed 2-of-3 wallet on testnet using supported available signers, safely receive/send test sats, inspect proper fees and outputs. No mainnet, no production credentials.
3. **Backup**: encrypted Mobile Key recovery blob, versioning, iCloud/Drive isolation, read-back verification, retry/offline/background/interrupted write tests; retain existing Keeper backup compatibility.
4. **Recovery via hardware**: lose/reinstall disposable preview, prove hardware possession, restore same wallet and explain retain-versus-rotate Mobile Key after restoration. This requires reviewed server protocol; do not simulate as if implemented.
5. **Recovery Contact**: enroll second person/device, approve/decline, backup/reinstall contact credential; recover when Keeper server is demonstrably unreachable. Actual independent channel/crypto is required for completion.
6. **Lost-key, inheritance and exit**: delay/veto/replacement, migration/archive/old deposit, Miniscript policy registration and exact signer paths, descriptor export plus actual compatible external-wallet sweep, with Keeper server offline.
7. **Hardening and mainnet-readiness**: comprehensive adversarial/destructive tests; iOS/Android real NFC/QR hardware and app life-cycle, independent crypto/security review, full regression against then-current Keeper build. Mainnet activation and campaign only after explicit user approval.

Each checkpoint may be smaller than the grouping above to keep visible feedback frequent. Keep a clean recorded matrix of **simulated / automated / native / physical / security-reviewed / user-tested**, never conflating these.
